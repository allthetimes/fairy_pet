## 3. 「四个角」——深靛蓝环带自己伸出的四根尖齿

> **结构性结论（重要）**：这四根尖齿**不是**贴在外圈蓝上的独立装饰，
> 而是**深靛蓝暗带本身的形状**——环带 + 四尖齿是**同一个几何体**。
>
> 证据（实测）：沿尖齿中心（213.5°）与环带中段（170°/258°）在同一半径上逐点比色，
> 在 u=0.66~0.76 区间最大色差仅 **5~13**（属噪声）；到 u≥0.78 才分叉，
> 那只是因为环带本身到 u=0.781 就结束了、亮蓝层开始，而尖齿继续往外延伸。
>
> 因此正确做法是**单一 path**（环带 + 四尖齿）+ **单一条 userSpaceOnUse 径向渐变**，
> 而不是"圆 + 4 个贴上去的多边形"。这样尖齿与环带之间没有接缝、渐变连续，
> 旋转时也是整个形状一起转（这才是真正的"齿轮"）。
>
> ⚠️ 渐变必须用 `gradientUnits="userSpaceOnUse"`：
> path 的包围盒含尖齿（r≈93），若用默认的 objectBoundingBox，渐变比例会整体失准。

| 参数 | 实测/标定值 |
|---|---|
| 尖齿数量 | **4 根** |
| 中心角度（图像坐标，0°=右，顺时针） | **33.5° / 123.5° / 213.5° / 303.5°** |
| 角度间距 | 严格 `90°` |
| 形状 | **线性收敛到 0 的真尖点**（不是梯形；顶端无平台） |
| 基底半径 | `u = 0.781`（即靛蓝带外缘 `r = 166px`） |
| 基底半角 | `12.5°` |
| 顶端半径 | `u = 0.93`（`r ≈ 198px`） |
| 颜色 | 与环带共用同一条径向渐变，向外持续加深变蓝 |

## 8.5 两个必须知道的坑（已实测确认）

### 坑一：SVG 元素上的 CSS `transform-origin` 会让旋转/缩放跑飞

**现象**：给 SVG `<g>` 加 `animation: rotate(...)` + `transform-origin: center`，
齿轮转 90° 后四个角**整个飞出画面消失**。

**原因**：CSS `transform-origin: center` 在 SVG 元素上解析的参照盒不是你以为的那个
（Chrome 下会落到元素边框盒，其中心在用户坐标系里离 viewBox 中心很远），
于是旋转变成"绕一个远在画外的点公转"。
补 `transform-box: view-box` 在实测中**仍然无效**。

**解法：改用 SVG 原生 SMIL 动画**。`<animateTransform>` 的 `rotate` / `scale`
恒以当前用户坐标系原点 `(0,0)` 为基准 —— 把圆心放在 `(0,0)` 就永远不会踩这个坑：

```html
<g id="gearSpin">
  <animateTransform id="gearSpinAnim" attributeName="transform" type="rotate"
                    from="0" to="360" dur="48s" repeatCount="indefinite"/>
  <g id="notches"></g>       <!-- 四个角的多边形 -->
</g>
```

附加好处：`svg.pauseAnimations()` + `svg.setCurrentTime(t)` 可以**确定性冻结到任意时刻**，
比 CSS 动画的 `animation-delay` 好测得多。

只作用在 **HTML 容器**上的 `transform`（浮游位移、点击回弹）不受影响，可以继续用 CSS。
`filter`（提亮、RGB 分离）也与参照盒无关，安全。

### 坑二：克隆 SVG 时重复的 `id` 会让填充变黑

克隆出的 `<defs>` 若与原 svg 同名，`url(#grad)` 会解析到文档中**第一个**匹配项；
而克隆体常放在 `display:none` 的子树里，隐藏子树中的 paint server 会导致**填充渲染为黑**。
必须给克隆体所有 `id` 加前缀，并同步重写所有 `url(#...)` 引用。

## 8.6 已确认的"非设计特征"（不要复刻）

| 现象 | 证据 | 结论 |
|---|---|---|
| 外圈蓝在底部扇区（35°~125°）明显偏暗：B≈179，其他三个扇区 B≥230 | 1.0 版同一位置反而**更亮**（B132 vs 其它 113~126）——两版符号相反 | 游戏 HDD 屏幕背光不均造成的环境产物，**不是 Fairy 的设计**。代码版保持径向对称 |
| 整张立绘带横向 CRT 扫描纹与整屏蓝色泛光 | 属于 HDD 屏幕的显示效果，不是角色本体 | 扫描线可保留（提升还原感），泛光按需 |

> 教训：从游戏截图反推设计时，**必须拿两个版本交叉验证**。
> 只在单一版本上出现的"不对称"，大概率是屏幕/后处理造成的。

## 12. 状态机（2.6+ 实测，A/B/C/D 四态）

**来源**：BV1J9R2BNEpU（8 分钟 1080p 视频，HDD 段 0–440s）。逐帧实测得到的状态机，
比 wiki 立绘多出 3 个非默认态（之前 09-13 漏掉的核心动效）。

### 12.1 状态 A：正常睁眼态（默认待机）

- 完整可见：白环 + 蓝环 + 中央深眼 + 高光球 + 4 尖齿 + 外白描边
- 附加：呼吸脉冲 ±2.8% / 0.9s，虹膜独立胀缩 ±1.8%（§11）
- **占 Fairy 在画面里 ~80% 的时间**

### 12.2 状态 B：长闭眼态（持续 ~30s）

**新发现**！这是 Fairy 在听玩家说话/处理任务时的状态，**不是瞬间眨眼**。

| 项 | 实测 |
|---|---|
| 触发 | 上一个动作结束 → 故障闪（0.66s）+ 白屏闪（0.23s）→ 进入 B |
| 持续时长 | **~30 秒**（v2_1 实测 54.13s → 86.50s） |
| 几何 | 上半圆被深色月牙覆盖，**底边沿 r=64.5 圆弧**（白环外缘），4 尖齿在外圈**独立可见** |
| 上眼睑颜色 | `#1A2094` ~ `#1E2080`（靛蓝层同色系） |
| 上眼睑覆盖范围 | **r=0 到 r=64.5 的上半圆**（白环内区） |

**关键认知修正（用户 2026-09-13 14:00 反馈）**：

> "你所说的角，其实和眼睑没关系，只是颜色一样。后面的四个角依旧是在转动的，眼睑跟着白色的那一圈"

4 个尖齿由 `gearSpin` 独立旋转，**几何上独立于眼睑**。**它们颜色恰好和眼睑一致**（都是深靛蓝），
所以闭眼时从远处看"似乎融在一起"，实际上是两个独立的元素。

**关键代码**（lab.html）：
```html
<g id="stateB_lid">
  <path d="M -64.5 0 A 64.5 64.5 0 0 1 64.5 0 Z" fill="url(#gLid)"/>
</g>
```

**实现要点**：
- 路径由 sweep=1 弧（经过上方）+ 水平直线闭合构成
- 弧半径 r=64.5 → 上眼睑**不覆盖外圈蓝（r>78.1）和 4 个尖齿（r=78.1~93）**
- 4 尖齿由 `#gearSpin` 独立旋转动画，**与眼睑无关**
- 颜色一致是**视觉错觉**，不是几何关系

### 12.2.1 呼吸动效修正（用户 2026-09-13 14:00 反馈）

#### 坐标和距离定义

- SVG 原点为环形核圆心 `(0,0)`，y 轴向下。
- **齿轮圆基准**不是外圈 `r=100`，也不是四个齿尖的外端 `r≈93`，而是靛蓝齿轮环带的连续圆弧外缘：`r_g = 78.1`。
- 眼睑底缘在同一圆心、同一角度 `θ` 上的半径为 `r_lid(θ,t)`。
- 主指标为眼睑到齿轮基圆的径向距离：

```text
D(θ,t) = r_g(t) - r_lid(θ,t)
```

  `D>0` 表示眼睑底缘位于齿轮基圆内侧；不能用眼睑到外圈 `r=100` 的距离替代。

**形状：纯缩放**

`θ 24°/150°` 为 0.02/0.04，`θ 6°/168°` 为 0.09/0.11。
⇒ 底缘形状基本固定，只有整体幅度在变；两个端点会随帽檐上下移动而左右滑动。

**底缘的形状：一条圆弧（单参数）**

底缘点集做圆拟合，残差 RMS 只有 **0.46%**（相对半径）—— 确实是圆弧，不是折线。
但用有限弧段（θ 15°~165°）外推圆心/半径是病态问题：拟合出的 `R_arc` 在 43~141 之间乱跳（±31），参数不可用。

改用"**过基圆两交点**"的参数化，只剩**一个自由度**：

```text
底缘圆弧必须经过 (±78.1, 0)   ⇒ 圆心必在 y 轴上 (0, cy)
半径满足   R² = 78.1² + cy²
令 bot = 圆弧最低点 y = cy + R  （即底缘中央的深度）
⇒ R = (78.1² + bot²) / (2·bot)
```

这样描出来的弧天然与齿轮基圆相接、无折角，参数也稳定。
实测该模型对逐帧底缘点的残差 **RMS 0.89px / 最大 1.91px**。
它同时解释了上面观察到的"纯缩放"：整条底缘只有 `bot` 一个自由度。

> ⚠️ **几何约束（关键）**：由 `y_mid = R − √(R²−R_G²)` 可知，**底缘中点恒在圆心或圆心下方**（`bot ≥ 0`）。
> 原因是这条弧必须连接基圆上的两个交点 (±78.1, 0)，弧只能向下凸。
> ⇒ 只靠改半径**越不过圆心**；要让中点移到圆心上方，必须让**眼睑整体平移**。

**端点固定 + d 动画**（2026-09-14 10:58 定稿）

需求（用户逐步明确）：① 底缘弧的两个**端点固定不动**；② 只有弧的**下垂深度**在变；
③ 呼吸收缩到最小时眼睑在最下面。

- 端点固定在基圆 **(±77.69, −8)** 不动（圆心上方 8 单位；`--ep-y` 可调）；
  每帧一条 path，只有底缘弧的半径 `R` 在变：

```text
M -77.69 -8 A 78.1 78.1 0 0 1 77.69 -8 A R R 0 0 1 -77.69 -8 Z
x0 = √(78.1² − ep_y²)
cy = (x0² + ep_y² − bot²) / (2·(ep_y − bot))
R  = bot − cy        （bot > ep_y 恒成立 ⇒ 弧始终向下凸，sweep 恒为 1，无翻转）
```

- **15 个关键帧/周期**（DP 自动），`bot` 在 **12.48**（呼吸谷，眼睑最下）↔ **1.15**（呼吸峰，眼睑最上）之间往复

  （⚠️ 这里摔过两次：折叠对齐曾用 argmin 把方向搞反，必须用 **argmax**，见"坑 14"）
- `dur` 由呼吸滑条驱动；`keyTimes` 保留实测的归一化波形（真实开合节奏）
- 折叠波形经环形中值平滑 + 幅度校正（折叠中位数会把极值收敛 −28%，须用 0.5/99.5 分位数拉回）

> **一段弯路（记下来防止再犯）**：
> ① 第一版 `<animate>` 放在了 `<g>` 里 —— SMIL 只作用于**父元素**的属性，
> `<g>` 没有 `d` 属性，动画**静默失效**；我却据渲染结果误判"Chrome 对圆弧 d 补间不可靠"。

> ③ "中点越过圆心"在几何上不可能（弧要接基圆两端 ⇒ `y_mid = R−√(R²−R_G²) ≥ 0`），
> 实测里中点的确只到 `+0.39`（贴着圆心），不会到上方。
> ④ 端点上移（`ep_y = −8`）之后矢高变大，"太平"的问题解决 —— 且 bot 恒 > ep_y，

#### 踩过的坑

1. **不能用蓝色掩膜找圆盘** —— 背景也是蓝的，会连成一片。要用最外细白描边（亮 + 低饱和）。
2. **亮度阈值判"深色"在 θ≈3°/177° 会误判** —— 那两个方向帽檐底缘与基圆即将交汇，
   帽檐内部亮度升到 59~69、`B-R` 掉到 61~66，写死的绝对阈值全部翻车。必须自适应基准 + 增量。
3. **`|dL/dr|` 全局极大抓到的是"灰紫蓝→白"（ΔL≈55）而不是帽檐底缘（ΔL≈25）**。
4. **增量必须小于"帽檐→深眼"的亮度差**（实测只有 ΔL≈20）——
   用 38 会跳过真正的底缘、抓到更外侧的"深眼→中蓝环"边界，`D(90°)` 直接从 163px 掉到 125px。
5. **上半部标定 `r_g` 要用色度 `B-R` 而不是亮度** —— 画面泛光会让深靛亮度整体抬升，
   亮度阈值整段失效且呈 ~1.5s 的周期性；`B-R`（深靛 61~115 vs 亮蓝 155~170）与整体亮度无关。
6. **帽檐底缘不等高** —— 最低点在 `θ≈63°~90°` 之间摆动，左右也不对称，不要假设它是对称圆弧。
7. **正则替换 `d="…"` 会先匹配到 `id="` 里的 `d="`**，把 `id` 属性吃掉。
   要匹配完整前缀 `<path id="closedLidPath" d="[^"]*"`。
8. **底缘必须用圆弧命令（`A`），不能用折线（`L`）**。
   折线在"底缘与基圆的交点"处会留一个难看的折角 —— 那里半径从 78 突降到 50，
   用 8° 步长的 `L` 就是一段直线，视觉上明显是"多边形"。
   而且这**同时**是用户指出"下半部分不是圆弧"的原因。
9. **折叠取平均会削掉幅度（−28%）**，动画会显得"根本没在动"。
   折叠出来的形状可以用，但幅度必须用分位数拉伸回实测极值。
10. **帽檐的 `dur` 必须跟呼吸环一起设**。写成固定值（0.852s）会与呼吸（滑条控制的 0.867s）
    失步，看起来就是"没跟着呼吸"。改 `applyBreath()` 时一并 set。
11. **折叠前先环形平滑**：折叠残差（0.8 SVG 级）会让 DP 为追逐这些小波动多给一倍关键帧。
12. **`<animate>` 必须是 `<path>` 的子元素** —— SMIL 只作用于父元素的属性。
    把它放在 `<g>` 里会去找 `<g>` 的 `d` 属性（不存在），动画**静默失效**，
    而且从 attribute 读回、语法检查都看不出来 —— 只有用渲染像素才能发现。
    本项目曾因此误判"Chrome 对圆弧 d 补间不可靠"，实际补间完全正常
    （最小化测试页 + 差异图复验，月牙形差异区清晰可见）。
    （另：底缘弧要接基圆两端 ⇒ 中点恒 `≥ 0`，这是几何限制，与浏览器无关。）
13. **量"底缘位置"时别用行内深色像素宽度的相对阈值** ——
    帽檐不覆盖圆心的相位，深色宽度只剩靛蓝环带那一条，相对阈值会误判到基圆底边。
    稳妥办法是看**圆心处的亮度**（帽檐覆盖时 ~41，未覆盖时 ~64）或直接目视。
14. **"谁最大/最小"的相位对应必须用实测确认，不能凭直觉** ——
    初版把映射写反了（让"帽檐最深"对应"眼睑中点在圆心上方"），
    用户一眼就看出"收缩到最小时眼睑应该在最下面"。
    核实办法：在同一个 freeze 时刻**同时量两个量** ——
    呼吸量（露出白环的像素面积，本例相位 0 → 13864、相位 0.6 → 18752）
    和运动量（中点 y，+14 ↔ −2），确认它们同向。只看单侧数据很容易反。
15. **（若用 clip + 平移方案）被裁的那一侧要"喂饱"** ——
    形状的上边界若用"半径 78.1 的上半圆弧"，平移后在两侧会凹进基圆内侧，
    视觉上"上面也在动"。要把上边界做成**远超裁剪范围的大矩形**，
    让 `clip-path` 裁出来的边界恒等于基圆本身。
    验证办法：对两个相位做 `absdiff` 并分区量化
    （本例上半部平均绝对差 0.04~1.7，下半部 9.5~20.6）。
    —— 本项目最终没采用这个方案（端点会跟着滑，被用户否掉），但技巧本身可复用。


**核心结构 95% 对齐**；环境效果（蓝色辉光、扫描线、屏幕泛光）属于 HDD 屏幕不是 Fairy 本体，不复刻。
