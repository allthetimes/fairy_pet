### 踩坑（都是"阈值/判据"类的，记牢）

1. **蓝色掩膜找圆盘不行** —— 背景也是蓝的，会连成一片。要用最外细白描边（亮+低饱和）。
2. **θ≈3°/177° 不能用绝对亮度阈值** —— 帽檐底缘与基圆即将交汇处，帽檐内部亮度升到 59~69、
   B-R 掉到 61~66，写死的阈值全部翻车。必须自适应基准 + 增量。
3. **`|dL/dr|` 全局极大抓到的是"灰紫蓝→白"（ΔL≈55）而不是帽檐底缘（ΔL≈25）**。
4. **增量必须小于"帽檐→深眼"的亮度差（实测只有 ΔL≈20）** ——
   用 38 会跳过真正的底缘、抓到更外侧的"深眼→中蓝环"，D(90°) 从 163px 直接掉到 125px。
5. **上半部标定 r_g 必须用色度 B-R，不能用亮度** —— 画面泛光让深靛亮度整体抬升，
   亮度阈值整段失效且呈 ~1.5s 周期性；B-R（深靛 61~115 vs 亮蓝 155~170）与整体亮度无关。
6. **帽檐底缘不等高** —— 最低点在 θ≈63°~90° 之间摆动，左右不对称，别假设对称圆弧。
7. **Python 正则 `d="…"` 会先匹配到 `id="` 里的 `d="`**，把 id 属性吃掉。
   要匹配完整前缀 `<path id="closedLidPath" d="[^"]*"`。
8. **关键相位用均匀采样而不是按曲率 DP** —— 端点上升沿比中央早约 43ms（相位错位），
   DP 会在端点段漏点（端点最大误差 17.8px 反而比均匀 24 点的 15.2px 差）。

### 方法学沉淀

- **"折叠 + 纯缩放"是压缩周期运动的利器**：先测准周期（扫 T 最小化折叠方差），
  再折叠成单周期波形。若各角度的归一化波形一致（cv 小），形状可固定、只留 1 个自由度。
- **视频开头常有 UI 过渡段**（这里是 IDE 界面→剧情画面，t<2.35s），
  圆心附近全黑、构图标定不同，必须用有效性判据丢掉（本脚本的 `--skip-sec`）。
- **ROI 裁剪 + `cap.grab()` 跳帧** 能把处理速度提到 80 帧/s（1080p 全图处理是纯浪费）。

## 第二轮修正（用户 2026-09-14 10:10 反馈）

> "首先你下半部分根本也不是圆弧，其次，你的动画也没随着呼吸而运动。"

两处都是真问题，第一版的做法错了。

### 1. 底缘必须是圆弧，不能用折线

第一版用 23 点折线（`L` 命令）描底缘 —— 在"底缘与基圆的交点"处，半径从 78 突降到 50，
8° 步长的折线就是一段直线，看着就是多边形。

**正解：底缘是一条圆弧，而且只有一个自由度。**

- 底缘点集做圆拟合，残差 RMS 仅 **0.46%**（相对半径）⇒ 确实是圆弧
- 但用有限弧段（θ 15~165°）外推圆心/半径是**病态问题**：R_arc 在 43~141 乱跳（±31），参数不可用
- 关键洞察：**圆弧必须过基圆两交点 (±78.1, 0)** ⇒ 圆心必在 y 轴上 ⇒ 只剩 1 个参数：

```
底缘圆弧过 (±78.1, 0)、最低点 (0, bot)
⇒ R = (78.1² + bot²) / (2·bot)

path = "M -78.1 0 A 78.1 78.1 0 0 1 78.1 0 A R R 0 0 1 -78.1 0 Z"
```

- 该模型对逐帧底缘点的残差 **RMS 0.89px / 最大 1.91px** ✓
- 这同时解释了"纯缩放"的成因（整条底缘只有 bot 一个自由度）
- **收益**：关键帧从 40 个 × 334 字符（13.7KB）降到 **15 个 × 65 字符（1.5KB）**

### 2. 帽檐必须与呼吸同周期

第一版把帽檐 `dur` 写死 0.852s，而页面的呼吸是滑条 `pBreath` 控制的 0.867s ⇒ 失步，
看起来就是"没跟着呼吸"。

**修正**：在 `applyBreath()` 里把 `closedLidPathAnim` 的 `dur` 与四个呼吸环一起 set。
真浏览器验证：`dur_lid == dur_breath == 0.867s`，滑条拖到 1.5s 后两者都变 1.5s ✓

帽檐的 `keyTimes` 从"最深"（bot 最小）开始，与呼吸的"谷"同相。

### 3. 顺带修掉的：折叠削幅

折叠取中位数会把极值收敛：摆幅 12.25 → 8.78 SVG（**−28%**），动画显得"没在动"。
修正：保留折叠出的**形状**，用 `0.5/99.5` 分位数把幅度线性拉伸回实测极值
（`--no-rescale` 可关）。修正后摆幅 11.33 SVG = 24.7px，接近原片 26.7px ✓

另外折叠前加**环形中值平滑**，去掉相位错位留下的 0.5 SVG 级抖动，
否则 DP 会为追这些小波动多给一倍关键帧。

### 教训

- **"看起来是圆弧"的东西，先用圆拟合验证残差，再想怎么参数化**。
  有限弧段外推圆的参数是病态的，改用"过已知两交点"的参数化能降到 1 个自由度，稳定且优雅。
- **幅度和周期是最容易被"平均/写死"偷掉的两样东西**，也是肉眼最先察觉的。
  折叠前先量一下原始极值，写 dur 前先确认它跟着谁走。

## 第三轮：按用户思路改用 translate 驱动（2026-09-14 10:23）

> "在第0帧（t=0）时，将下方圆弧的中点定位在同心圆圆心上方一点；在该周期最后一帧时，
> 将其定位在圆心下方一点；通过在周期内让该中点从圆心上方平滑移动到圆心下方，
> 从而实现圆弧形眼睑的开合运动。"

### 两个关键发现

**1. 底缘弧的中点几何上越不过圆心**

底缘弧必须连接齿轮基圆两端 (±78.1, 0)（否则外缘有缝），弧只能向下凸：

```
y_mid = R − √(R² − 78.1²)  ≥ 0   恒成立（R→∞ 时 → 0）
```

所以**只改半径做不到"中点在圆心上方"**。要越过圆心，必须让眼睑**整体平移**。

**2. `<animate attributeName="d">` 改圆弧半径在 Chrome 里不可靠**

上一版用 15 条 path（只有 `A` 的半径在变）做 d 动画，
实测 **7 个相位下渲染出的底缘只动 3px**，而数据里应有 24px ——
即 SMIL 对"只有半径在变的圆弧"补间失真。

### 最终实现：形状固定 + translate + clip

```html
<clipPath id="lidClip"><circle r="78.35"/></clipPath>

<g id="stateB_lid_top" style="display:none" clip-path="url(#lidClip)">
  <path id="closedLidPath"
        d="M -78.1 0 A 78.1 78.1 0 0 1 78.1 0 A 429.89 429.89 0 0 1 -78.1 0 Z"
        fill="url(#gLid)">
    <animateTransform id="closedLidMoveAnim" type="translate"
                      values="0 -9.15;…;0 6.85" keyTimes="…" dur="0.867s" repeatCount="indefinite"/>
  </path>
</g>
```

- 形状固定（取实测中位数那条弧）；`translate` 从 **+6.85（闭）** 到 **−9.15（开）**
- ⇒ 底缘中点 y 在 **+14.00（圆心下方）** 与 **−2.00（圆心上方）** 之间往复，摆幅 **34.9px**
- **相位对应**（初版写反了，用户 2026-09-14 10:36 指出后修正）：
  相位 0 = 呼吸**谷**（内环收缩到最小）→ 眼睑**最下**（中点 +14.00，露出白环最少 13864px²）；
  相位 ≈0.6 = 呼吸**峰** → 眼睑**最上**（中点 −2.00，露出白环最多 18752px²）。
  即"收缩到最小时眼睑运动到最下面"。
- `clip-path` 裁到齿轮基圆 ⇒ 平移时外缘恒贴合基圆，不会露出缝
- `dur` 仍由呼吸滑条驱动；`keyTimes` 保留实测的归一化波形（真实开合节奏）
- 关键帧数据 1.5KB → **0.9KB**

**注意**：用户描述"第0帧在上方、末帧在下方"是单向的，但动画要循环，
所以做成**往复**（相位 0 最下 → 0.6 最上 → 1 回到最下），周期与呼吸一致。

### 验证

- 真浏览器：`dur_lid == dur_breath == 0.867s`，拖滑条到 1.2s 两者同步；
  点击 3 次 display 依次 `''/none/''`；无 JS 错误
- 渲染实测：**圆心处亮度 t=0 时为 64（帽檐未覆盖）→ t=0.52 时为 41（深靛覆盖）**
  ⇒ 底缘确实从圆心上方移到了下方
- 七相位对照图 `dev/shots/lid_translate_phases.png`

### 教训

- **先做几何可行性推导再写代码**。用户要"中点越过圆心"这件事，如果一开始就推
  `y_mid = R−√(R²−R_G²) ≥ 0`，就能立刻知道"改半径"这条路走不通，省一整轮返工。
- **SMIL 的 `d` 动画只适合"命令结构相同且各参数都按比例变"的路径补间**；
  像"只有某个弧的半径在变"这种，Chrome 的表现不可靠 —— 实测像素才敢下结论。
- **量位置别只看一处**。本轮我先用"行内深色像素宽度的相对阈值"量底缘，在帽檐不覆盖
  圆心的相位误判到基圆底边；改看"圆心处亮度"才得到正确结论。
- **⭐ "谁最大/最小"的相位对应不能凭直觉，要用实测双量确认**。
  我把"帽檐最深"映射到了"眼睑中点在圆心上方"，正好反了，用户一眼看出。
  核实办法：在同一 freeze 时刻**同时量呼吸量和运动量** ——
  呼吸量用"露出白环的像素面积"（相位 0 → 13864、相位 0.6 → 18752），
  运动量用"中点 y"（+14 ↔ −2），确认它们同向。只看单侧数据极易搞反。

## 第五轮：真相大白 —— d 动画一直是好的，是我把 `<animate>` 放错了地方（2026-09-14 10:58）

> "圆弧两个端点也是不会动的"

**用户的连续三次反馈串起来才是完整需求**：端点不动、上面不动、只有底缘弧的下垂深度在变。

**破案过程**：做一个最小化测试页（单 path + 单 `d` 动画 + 差异图），
差异图里出现清晰的**月牙形差异区** ⇒ `d` 动画补间完全正常。

**真正的 bug**：之前把 `<animate>` 放在了 `<g>` 里 ——
**SMIL 只作用于父元素的属性**，`<g>` 没有 `d` 属性 ⇒ 动画**静默失效**，
而 attribute 读回、语法检查都看不出来。我却据渲染结果误判"Chrome 圆弧补间不可靠"。

**最终实现**（回到 d 动画，端点固定）：

```html
<g id="stateB_lid_top" style="display:none">
  <path id="closedLidPath" d="M -78.1 0 A 78.1 78.1 0 0 1 78.1 0 A 2658.56 2658.56 0 0 1 -78.1 0 Z"
        fill="url(#gLid)">
    <!-- ⚠️ 必须在 <path> 内部 -->
    <animate id="closedLidMoveAnim" attributeName="d" values="…15 条 path…"
             keyTimes="…" dur="0.867s" repeatCount="indefinite"/>
  </path>
</g>
```

- 端点固定 (±78.1, 0) 不动 ✓；上半圆恒贴合基圆 ⇒ "上面静止"自动成立 ✓
- bot 在 **1.15**（呼吸谷，眼睑最下）↔ **12.48**（呼吸峰，眼睑最上）往复
- 实测：上半部 absdiff **0.027**（静止）、下半部 **18.0**（运动）、两端点邻域 **3~4** ✓
- 15 关键帧、1.5KB；中途的 translate/clip 方案全部废弃

### 教训（本轮新增）

- **⭐ SMIL `<animate>` 只作用于父元素**。`d` 动画失效时，第一件事是检查
  `<animate>` 是不是 `<path>` 的直接子元素 —— 别先怀疑浏览器。
- **被推翻的结论要回头复验**。"Chrome 补间不可靠"这个错误结论流传了三轮，
  根因只是一个 DOM 位置错误。用最小化用例隔离变量，才能定位真因。

## 第七轮：帽檐与呼吸的 begin 对齐（2026-09-14 11:40）

> "周期对齐一下？眼睛到最下面的时候通孔收缩到最小，这是同时的"

**问题**：各呼吸环有 0~96ms 的 `begin` 阶梯（内环最先动，白环 +96ms），
而帽檐 `begin=0` ⇒ 与白环天生错开 96ms —— 用户看到的"不同时"就是这个。

**实测**：把眼睑深度(bot) 与 白月牙下边缘(白环外缘 y) 做**互相关**
（911 帧采样，x=cx 列）—— **r=0.94，眼睑最下比白环最小晚 41.7ms**。

**修正**：`applyBreath()` 里帽檐 `begin = 白环 begin(0.096) + 0.042 = 0.138s`。
真浏览器验证：`lid.begin=0.138s`、滑条拖动后保持、`lag_ok: true`。

### 教训（本轮）

- **多元素动画的"同时"不是 begin=0 就完事** —— 各元素的 begin 阶梯是隐形的
  相位偏移，必须逐一核对。
- **时差用互相关实测**（这里 bot vs 白环外缘 y，r=0.94），别猜。
  顺带：互相关的符号方向（谁滞后谁）很容易读反，打印表格时要把
  "正 = 谁滞后谁"写清楚，或者干脆用绝对时差 + 常识判断。

## 第四轮：让上半部静止（2026-09-14 10:47）

> "原版只有下面的圆弧会运动，上面是不会动的，你能不能改一下让上面静止。"

**问题**：上一版形状是"半径 78.1 的上半圆弧 + 底缘弧"，整体 translate 平移
⇒ 上半圆弧跟着移动，在两侧凹进基圆内侧 ⇒ 视觉上"上面也在动"。

**修正**：把形状的上边界做成**远在基圆之外的矩形**：

```
M -90 -140 L 90 -140 L 90 0 A 569.70 569.70 0 0 1 -90 0 L -90 -140 Z
```

- `margin=90 > R_G=78.35`、`top=-140` 远超基圆顶部
- clip 到基圆后，裁剪出的上边界**恒为齿轮基圆本身**，与 `translate` 无关 ⇒ 上静止
- 底缘弧仍过 (±90, 0)、最低点 7.15 ⇒ `R = (90² + 7.15²)/(2×7.15) = 569.7`

**验证**：对两个相位做 `absdiff` —— 上半部平均绝对差 **0.04~1.7**（抗锯齿级，
差异图里上半部全黑），下半部 **9.5~20.6** ✓ 相差一个数量级。
（`dev/shots/lid_static_top_check.png`）

### 教训

- **⭐ 平移驱动的元素，被裁的那一侧要"喂饱"**：上边界不能用"刚好贴合"的形状
  （这里不能用半径 78.1 的半圆），要用远超裁剪范围的大矩形，
  让 clip 裁出来的边界恒等于目标（基圆）⇒ 那部分就静止了。
- **"哪部分在动"要用 absdiff 分区量化**，别只看整体。把区域分成"应该静止"和
  "应该运动"两块分别算平均绝对差，比值差一个数量级才算数。

## 桌宠 v0.2 修复（用户 4 条反馈，2026-09-14 21:00–21:45）

> "1.拖动不了。2.去掉边框，文本框都显示不全，高光也显示不全，不需要边框。3.需要能改大小，设置里自行按百分比设置。4.默认位置在屏幕右下角。"

### 根因 1：拖动不了 = **Tauri v2 的 capabilities 权限没配**（漏建文件）

Tauri v2 引入了权限系统，**默认不给前端任何窗口 API 权限**。
我建工程时漏了 `src-tauri/capabilities/default.json`，导致 `startDragging()`、`event.listen`、
`setSize` 全部被拒绝（且**静默失败**，不报错）。

**修复**：新建 `capabilities/default.json`，授予：
`core:default` + `core:window:allow-start-dragging` + `allow-set-size` + `allow-set-position` +
`core:event:allow-listen` + `allow-emit` + `autostart:default` + `global-shortcut:default`。
⚠️ 权限名可用 `gen/schemas/desktop-schema.json` 里的 grep 校验（编译时也会校验）。

### 根因 2：窗口有边框 = **Tauri 的 `decorations:false` / `transparent` 在 Win11 上不生效**

实测证据（用 Python ctypes 读窗口样式位）：
- conf 里 `decorations:false` + `transparent:true` + `skipTaskbar:true`，但窗口实际
  `WS_CAPTION=True`、`WS_BORDER=True`、`WS_EX_APPWINDOW=True`（有标题栏+边框+占任务栏）
- **`win.set_decorations(false)` 返回 `Ok` 但样式位一个都没变**（tao 在 Win11 上的 bug）
- 用 Win32 API 直接改样式位 **立即可生效** ✓

**修复**：`main.rs` 里加 `force_frameless()`，用 raw FFI 调 user32：
```rust
GetWindowLongW/SetWindowLongW(h, GWL_STYLE, style & !(WS_CAPTION|WS_THICKFRAME))
GetWindowLongW/SetWindowLongW(h, GWL_EXSTYLE, ex & !WS_EX_APPWINDOW)
SetWindowPos(h, 0,0,0,0,0, SWP_NOSIZE|SWP_NOMOVE|SWP_NOZORDER|SWP_NOACTIVATE|SWP_FRAMECHANGED)
```
⚠️ **不要手动加 WS_EX_LAYERED**：Tauri 的透明走 DWM/WebView2 合成（ImageGrab 抓窗口会
抓到背后内容，正是透明的证据），手动加 LAYERED 会让窗口消失。
⚠️ 需要 `unsafe extern "system"` 语法（Rust 1.82+）。

### 根因 3：气泡/高光显示不全 = **窗口太小 + SVG viewBox 裁切**

- 窗口 420×420 而 `.pet` 填满 body ⇒ 气泡（在 .pet 上方）**完全在窗口外**
- 辉光 r=135 单位 > viewBox ±120 ⇒ 被 SVG 自身裁切
**修复**：窗口 500×600；`#svg{overflow:visible}`；布局改 `body{display:flex;align-items:flex-end}`
+ `padding-bottom`，气泡用 `bottom:100%` 贴圆盘上方。

### 新功能：缩放（设置里按百分比）

- 基准 窗口 500×600 / SVG 400px；scale 0.5–2.0
- CSS 变量 `--s` 驱动气泡字号/内边距等比缩放；SVG 尺寸 + 窗口尺寸由 JS 同步设置
- 设置窗口新增"桌宠大小"滑块（50–200%），storage 存**系数**（非百分比）
- debug 钩子：`?scale=1.5`

### 新功能：默认右下角

`setup` 里用 `current_monitor()`（兜底 `primary_monitor()`）算物理坐标，
`set_position` 到 `(屏宽-窗宽-24, 屏高-窗高-24)`。实测 (1396,456)，边距 24px ✓

### ⚠️ 最大的坑：改了 `pet-app/ui/*` 之后 `cargo build` **不生效**

**现象**：改了 index.html（布局/缩放/诊断代码），反复 `cargo build`，exe 里跑的还是旧前端。
表现为"无论怎么改都没反应"，浪费了大量排查时间。

**证据链**：
1. 页面用 HTTP 上报（不依赖任何 Tauri API）自证：真机 exe 上报的是**旧字段**（EVT），新字段（INTERNALS）从没出现
2. Chrome 打开**源文件**能正常上报新代码 ⇒ 代码没问题，是**嵌入**的问题
3. `out/tauri-codegen-assets/` 目录里累积了 **15 个** index.html 副本（内容哈希命名，大小递增）

**根因**：cargo 的增量编译只监控 `src-tauri/**`；改 `../ui/*` 不触发 `generate_context!`
宏重新展开，嵌入 exe 的仍是旧资源。

**修复**：`build.rs` 里补 `cargo:rerun-if-changed=../ui`（及各文件）+
清掉 `target/debug/build/fairy-pet-*/out/tauri-codegen-assets` 后重建。
**以后改 ui 后若发现不生效，第一反应就是这里。**

**诊断手法（值得复用）**

**"页面自证"上报法**：页面 `fetch('http://127.0.0.1:8899/diag?info=...')` 把状态发给本机
Python http server（`scripts/diag_server.py`），绕过一切可能失效的 API 通路。
比 `document.title`（无边框窗口不更新标题）、`ImageGrab`（抓不到透明窗口内容）、
`console.log`（拿不到）都可靠。

**⚠️ 补充（当晚实测修正）**：`fetch` 会被 Tauri 的 CSP 拦掉，**用 `new Image().src = url` 最稳**
（img 用 no-cors，不受 CSP 的 connect-src 限制）。
且**不能放 setTimeout 里**——WebView2 会节流无焦点窗口的定时器，2.5 秒的定时器可能几十秒都不触发，
表现为"上报永远不来"。**改成同步执行**立刻拿到结果。

### ⭐ 真正的根因（排查了两小时，值得单列）

**现象**：改了 `pet-app/ui/*` 后 `cargo build`，真机跑的还是旧前端。
用户反馈的"气泡/高光显示不全"其实就是 **Phase 2 时的旧布局**（420px 窗口裁切）——
意味着**从 Phase 2 之后所有前端改动都没进过 exe**。

**排查过程（走了不少弯路）**：
1. 先怀疑 assets 缓存 → 解压 `target/debug/build/.../tauri-codegen-assets/*.html`（brotli 压缩，
   用 `node -e "zlib.brotliDecompressSync"` 解开）→ 内容其实是**对的**
2. 怀疑 WebView2 缓存 → 清了 `EBWebView/Default/{Cache,Code Cache,GPUCache}` → 无效
3. 怀疑进程残留（single-instance 把新进程干掉了）→ 严格杀干净 → 无效
4. 用 `<img src=...>` 探针确认**页面确实加载了**（不依赖 JS），
   再用 `__probe(1..4)` 分段探针确认**主脚本完整执行了**
5. 最后用**同步** img 上报拿到真相：
   `K[app,core,dpi,event,image,menu,mocks,path,tray,webview,webviewWindow,window] INTERNALS=true IINVOKE=true`
   → **`__TAURI__` 一直是好的**，`applyScale(1.5)` 也确实生效（窗口变 750×900）

**结论**：前端从来没有"API 不可用"，只是 **exe 里嵌入的是旧前端**。
**根因**：cargo 不因 `../ui` 变化而重新编译 `main.rs` ⇒ `generate_context!` 宏不重新展开 ⇒ 嵌入旧资源。
**解决**：改 ui 后 **`touch src-tauri/src/main.rs`** 再编译（build.rs 里写 `rerun-if-changed=../ui` 也不够可靠）。

**如果早点用"页面自证 + 分段探针"，能省一小时。**
教训：**"改了没反应"时，第一步就该确认"改动到底有没有到达运行中的程序"**，
而不是去猜它为什么表现异常。

## 桌宠崩溃修复（用户 22:09 反馈 panic）

> 用户贴出的错误：`Failed to setup app: error encountered during setup hook:
> HotKey already registered: HotKey { mods: Modifiers(ALT), key: F1, id: 65696 }`

**两个叠加的问题**：

**① 快捷键插件注册了两次** → `main.rs` 里 Builder 链上
`.plugin(global_shortcut::Builder::new().build())`，`setup` 里又
`app.handle().plugin(...with_handler...)`。第二次注册 Alt+F1 时判定"已注册"。

**② Alt+F1 是系统级全局热键** → 只要还有一个 fairy-pet 进程活着（哪怕是僵死进程），
新进程 `register` 就失败。而 `register(...)? ` 的 `?` 会把错误传播成 **setup panic
→ 进程启动后立即崩溃**（这比"注册不上"严重得多）。

**修复**（`main.rs`）：
- 删掉 Builder 链上那次 plugin 注册，只在 `setup` 里注册一次（带 handler）
- `app.handle().plugin(...)` 与 `register(...)` **全部改成容错**：失败只 `eprintln!` 警告，
  绝不 panic —— 快捷键被占用时桌宠照常运行，用户可用托盘菜单显示/隐藏

**验证**：僵死进程还占着 Alt+F1 时启动 → 日志打印
`[快捷键] Alt+F1 注册失败（可能被其它程序占用）`、**进程正常运行不崩溃** ✓；
清掉僵死进程后重启 → **注册成功**（日志无警告）✓

**③ 僵死进程处理**（顺带踩到的坑）：
`taskkill /F /IM` 和 `taskkill /F /PID` 都报"没有此任务的实例在运行"但进程仍在
（已终止但句柄未释放 —— **锁着 exe + 占着全局热键**，还留了一个带边框的旧窗口）。
- 绕文件锁：`CARGO_TARGET_DIR=target_run cargo build`（换输出目录，代价是全量重编 4.5 分钟）
- 真正杀掉：**Win32 `OpenProcess(PROCESS_TERMINATE)` + `TerminateProcess`** ✓ 一次成功
  （Python ctypes 调用，见本次会话命令）

**结论**：以后遇到"改了什么都没反应"，先确认**是不是有僵死进程在跑旧代码**。
